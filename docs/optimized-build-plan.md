# Optimized path: a static, state-normalized build

## The idea in one sentence

> Learn the **incremental value of item choices after accounting for the game states in which players bought them**, then publish one fixed build route for a champion, role, matchup and patch that performs well across plausible ahead, even and behind games.

**Game state is a training adjustment, not a live input.** Being ahead, behind, or on a strong team must not by itself make an item look powerful. The model should compare alternatives in comparable states, then average those comparisons over a predeclared reference mix of states. Give ahead, even and behind games deliberate representation and penalize routes that only look good when already winning. There is no single build guaranteed to be best in every game; the product goal is the most **robust, evidence-supported static route** for the selected pregame context.

## What the visitor sees

- Add an **Optimized path** tab beside **Most played** and **Higher observed WR**. Keep the existing observed paths as baselines, not as aliases for the model's recommendation.
- Before a match, select champion, role, lane opponent and patch. Use known draft information only if the website explicitly asks for it. The resulting ordered item-and-boots route stays fixed throughout the match; there is no live overlay, live PC connection or mid-game replanning.
- Show the complete route using the existing animated path. Explain why it differs from the most played route, its estimated advantage and uncertainty, how consistently it performs across ahead/even/behind strata, and the model version, patch coverage and effective sample size. Never put an observed win rate on a generated path as if that whole path had been played.
- If the model cannot distinguish candidates, say **No reliable optimized path yet** and show the most played build. Do not silently promote an unstable estimate.

## Work plan

1. **Define purchase decisions.** Reconstruct real choices and the state strictly before each one: champion, role, lane opponent, patch, side, gold/XP and objective leads, recent fights, inventory, prior purchases, elapsed time and enemy itemization. Use that state only during training and evaluation. Compare alternatives legal for the patch and plausible under the recipe and budget. Riot Match-V5 frames are periodic, so exact shop gold and some intentions are unknown; record that uncertainty. Use patch-specific [Data Dragon item data](https://developer.riotgames.com/docs/lol).
2. **Estimate state-adjusted item value.** Train an outcome model and an item-choice propensity model, then use cross-fitting and overlap-aware, doubly robust comparisons. Share information across related matchups and item roles with shrinkage. The existing `pipeline/item_research.py` is a read-only pairwise prototype; `pipeline/wpa.py` predicts game outcome, but its residuals alone are not an item-effect model. [Doubly robust learning](https://www.pywhy.org/EconML/spec/estimation/dr.html) still requires important reasons for a purchase to be observed.
3. **Normalize to a reference mix of games.** For each pregame context, average item comparisons over a fixed, documented distribution of early-game states rather than the states in which an item's buyers happened to be. Check ahead, even and behind strata separately. Optimize expected outcome with a penalty for uncertainty and severe downside in any stratum. Do not claim a route is universally best: this is a robust compromise for an unknown future game state.
4. **Evaluate complete fixed routes.** A first item changes later timing, gold and available choices, so do not simply add item scores. Generate legal candidate routes (including observed three-item cores), score each as a *sequence*, and compare its estimated held-out value with the most played route. Extend to later slots only when support exists; mark late items with weaker evidence rather than pretending every six-item sequence was observed. Sequential treatment methods such as [Dynamic DML](https://www.pywhy.org/EconML/spec/estimation/dynamic_dml.html) are candidates, not automatic solutions.
5. **Validate the recommendation, not just win prediction.** Freeze features and reference-state weights before testing on later matches/patches, separated by match and player history. Inspect ranking stability across splits, regions and game-state strata; propensity overlap, effective sample size, calibration, placebos and sensitivity to unmeasured skill or intent. A high outcome AUC does not pass this gate. The current 8,711-match export has no item-impact slot passing its split-half check. [EconML's validation guide](https://www.pywhy.org/EconML/spec/validation.html) explains why observational counterfactuals remain uncertain.
6. **Publish a versioned static route artifact.** Export only aggregate recommendations and evidence, never raw matches or player IDs. Include schema/model version, training cutoff, patches, pregame context, ordered route, uncertainty, state-stratum checks and fallback reason. Validate the complete artifact before switching the site's manifest. A site-wide data store can refresh this artifact without a production code deploy; the website remains static from the visitor's perspective, and the last good version stays available if training or upload fails.

## First release gate

The Optimized path tab can ship in an **experimental** state only after a fixed route beats the observed baseline in a forward-held-out evaluation with adequate overlap, stable ranking across game-state strata and a predeclared uncertainty rule. Otherwise the tab explains what evidence is missing and the observed build remains the recommendation. The 4090 may accelerate comparison experiments with a GPU-capable learner, but repeated fits to the same biased decisions cannot establish item impact.

Success means a player can answer before the match: **“For this champion and matchup, what fixed build is most likely to hold up whether my game starts well or badly, why, and how sure are we?”**
